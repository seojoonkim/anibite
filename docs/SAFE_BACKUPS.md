# 안전한 SQLite 백업·운영 적용 전 체크리스트

## 현재 변경의 범위

이 브랜치의 GitHub backup-db 워크플로는 운영 백업이 아니다. 합성 임시 DB로 백업 도구를 검사하는 수동 self-test만 한다. 운영 데이터 다운로드, 토큰 사용, artifact/release 첨부, 원격 삭제를 하지 않는다. 기존 자동 스케줄은 코드에서 제거했다. 아직 push/배포하지 않았으므로 기존 원격 워크플로 상태는 바뀌지 않았다.

기존 워크플로는 실행 중인 SQLite 파일을 직접 복사하고 DB를 GitHub release에 붙이도록 작성돼 있었다. 실제 과거 실행·노출 여부는 이 작업에서 확인하지 않았다. 운영자는 이 브랜치를 적용하기 전에 기존 workflow run/artifact/release 접근 권한과 노출 여부를 조사해야 한다. 노출이 확인되면 단순 파일 삭제로 끝내지 말고 비밀키 교체·세션 만료·필요한 보안 대응을 진행한다.

## 제공하는 로컬 도구

`python scripts/verified_sqlite_backup.py SOURCE_DB NEW_SNAPSHOT_PATH`

- 반드시 실제 DB가 위치한 호스트에서, 권한이 있는 운영자가 명시적으로 실행한다.
- source는 존재해야 하며 읽기 전용으로 연다. 오타 경로에 빈 DB를 만들지 않는다.
- sqlite3 backup API를 사용하므로 WAL에 남아 있는 커밋도 포함하는 일관된 snapshot을 만든다.
- snapshot `PRAGMA integrity_check`, 크기, SHA-256을 JSON으로 출력한다. SHA는 암호화가 아니다.
- 생성 파일은 0600이다. 목적지 파일은 절대 덮어쓰지 않는다.
- SQLite snapshot 복사 단계에는 기본 30초 제한이 있으며 `--timeout`으로 조정한다. 이후 integrity_check·해시 계산·fsync 시간은 이 제한에 포함되지 않는다. 실패 시 미완성 임시 파일을 제거한다.
- DB를 네트워크 전송하거나 원본을 수정·삭제하지 않는다. 외부 백업 서비스와 스케줄러는 포함하지 않는다.

실행 확인: `python -m unittest discover -s scripts/tests -v`
테스트는 새 임시 폴더의 합성 DB만 사용한다.

## 자동 운영 백업을 다시 켜기 위한 필수 조건

1. 현재 서비스 호스트·DB 경로를 운영자가 확인한다. `railway run`은 원격 쉘 실행을 대신한다고 가정하지 않는다.
2. 운영 DB 위치에서 위 도구로 일관된 snapshot을 만든다. 직접 live .db 파일만 복사하지 않는다.
3. 검증된 조직 관리 키로 암호화한 후 접근 제한된 비공개 저장소로 전송한다. GitHub release나 공개 bucket에 올리지 않는다.
4. 저장소 IAM, 키 보관·교체, 보관 기간, 실패 알림, 복구 목표를 정한다. 백업 미실행을 성공으로 보고하지 않는다.
5. 별도 환경에서 실제 백업을 복원하고 integrity_check, 사용자·평가·활동·댓글·좋아요·팔로우 집계, 로그인/평가 API를 점검한다.
6. 테스트한 스케줄러와 원격 실행 경로만 활성화한다. 이 문서의 존재는 자동 백업이 설정됐다는 뜻이 아니다.

## 마이그레이션과 복원

쓰기 중지 또는 단일 release job으로 동시 변경을 제어한다. 새 snapshot과 현재 앱 버전을 기록한 후 dry-run → 승인된 migration → 검증을 수행한다. 실패 시 새 앱의 쓰기를 중지한 다음 이전 앱과 호환되는 snapshot을 별도 검증하여 복원한다. 운영 복구는 자동으로 실행되지 않는다.
