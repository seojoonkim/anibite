# AniBite 리팩토링 검수·기획안

대상: https://github.com/seojoonkim/anibite

## 0. 결론과 검수 범위

**전면 재개발보다 기존 기반을 살리는 점진적 리팩토링을 권한다.** 제품의 중심은 ‘작품을 찾고 → 빠르게 평가하고 → 내 취향 기록을 쌓고 → 다른 팬과 나누는 경험’이다. 기능별 메뉴와 중복 상태를 이 흐름에 맞게 정리한다. 색상 변경이나 프레임워크 교체보다 데이터 정확성과 저장 신뢰성이 먼저다.

확인한 것:
- 운영 도메인의 공개 로그인 화면: 데스크톱 1280×633, 모바일 에뮬레이션 390×844. 화면·computed CSS·폼 label 연결을 확인했다.
- 저장소의 라우팅, 화면 컴포넌트, 네트워크 처리, API 계약, 데이터 쓰기와 마이그레이션 코드.
- 프런트엔드 실제 설치·프로덕션 빌드·린트·의존성 감사 출력.

확인하지 못한 것:
- 로그인 후 작품/캐릭터 상세, 피드, 평가, 프로필의 실제 화면 및 저장 왕복 동작.
- 실제 iOS/Android 기기, 키보드 전체 여정, 일반 브라우저 Google 로그인 성공 여부.
- 운영 DB, 서버의 추가 접근제어, 트래픽, API p95, 인증 후 LCP/INP/CLS 및 사용자 이탈률.
- 백엔드는 시작 시 DB 변경 작업이 있어 기동하지 않았다. 운영 관리 API를 호출하거나 사용자의 평점·리뷰·설정을 변경하지 않았다.

로그인 제약:
검수용 별도 Chrome에서 Google의 ‘브라우저 또는 앱이 안전하지 않을 수 있습니다’ 메시지가 사용자에게 표시됐다. Google은 소프트웨어 자동화 브라우저의 로그인을 제한할 수 있다고 안내한다. 이것을 AniBite 자체 OAuth 장애로 집계하지 않는다. 우회·보안 완화·세션 토큰 복사는 하지 않는다.
출처: https://support.google.com/accounts/answer/7675428?hl=en

이 문서의 ‘화면 확인’, ‘코드 확인’, ‘위험/가설’, ‘제안’은 서로 다른 증거 수준이다. 로그인 이후 디자인 제안은 코드 기반의 설계 방향이며 전체 화면 실사용 검수 완료를 뜻하지 않는다. 배포된 코드가 해당 Git 커밋과 완전히 같다는 것도 입증하지 않았다.

## 1. 현재 진단

### A. 디자인·브랜딩

1. **화면 확인 — 주요 로그인 버튼이 비활성 버튼처럼 보인다.** 실제 disabled는 false이고 배경은 rgb(30,39,54)다. Login.jsx:129의 파란색 지정이 index.css:243-248의 `button[style*="background"] !important`에 덮인다. 단순 취향 문제가 아니라 의도한 강조색이 적용되지 않는 CSS 결함이다.
2. **화면 확인 — 로그인은 영어, Google 버튼은 한국어로 혼재한다.** Login.jsx의 고정 영어 문구와 document lang=en, 앱 기본 언어 ko가 일관되지 않다. label과 input 연결도 두 필드 모두 0개로 확인했다.
3. **코드 확인 — AniBite/AniPass와 도메인 메타 정보가 혼재한다.** GitHub homepage의 anipass.vercel.app은 HTTP 404 DEPLOYMENT_NOT_FOUND. CNAME은 anibite.com. index.html의 OG/description도 확인·통일이 필요하다.
4. **코드 확인 — 디자인 토큰은 있으나 전역 강제 덮어쓰기와 인라인 색상으로 적용 규칙이 갈라져 있다.** 토큰을 새로 더 만드는 것보다 CSS 적용 경계를 정리해야 한다.

유지할 자산: 어두운 배경, 하늘색 AniBite 로고/강조색, 금색 평점. 새 브랜드를 만들기보다 ‘작품 포스터가 주인공인 취향 기록 서비스’로 다듬는다.

### B. 사용성·정보구조

1. **코드+공개 진입 확인 — 가치 확인 전에 로그인해야 한다.** `/`, `/browse`, `/anime/:id` 등이 ProtectedRoute다. 작품을 구경하거나 공유 링크를 보기 전부터 가입을 요구한다. 공개 카탈로그/상세는 열고 개인 기록과 쓰기에서 인증하는 방향을 권한다. 이는 제품 정책 변경이며 단순 버그 수정은 아니다.
2. **코드 확인 — ‘평가·캐릭터 평가·리뷰 작성·탐색·피드·리더보드’가 기능별로 나뉜다.** Navbar.jsx:183 이후. 사용자는 작품에 대해 평가·저장·리뷰를 연속 수행하려는데 다른 기능 영역을 이해해야 한다.
3. **코드 확인 — 로그인 후 원래 상세 링크로 돌아가지 않는다.** ProtectedRoute는 목적 URL을 넘기지 않고 Login.jsx:28은 `/`로 이동한다.
4. **코드 확인 — 별점의 반점 선택이 포인터 좌표에 의존한다.** StarRating.jsx:50-64,153-166에 접근 가능한 이름·선택 상태가 없고 키보드 반점 선택 계약도 없다. Rate 카드의 hover 조작과 링크 안 버튼 중첩은 터치/키보드 재검수 대상이다.
5. **코드 확인 — 모달·오류 회복이 화면별로 다르다.** EditReviewModal의 dialog/focus/Escape 설계가 없고, 일부 피드 실패는 빈 배열로 바뀌어 ‘없음’과 ‘실패’가 섞인다. 공유 컴포넌트와 공통 상태 규칙이 필요하다.

### C. 반응속도·데이터 정확성

1. **코드 확인 — Browse 요청 계약 불일치.** 프런트는 limit/sort를 보내고 서버는 page_size/sort_by를 받는다. sort 값의 enum 변환도 필요하다. `setPage` 직후 이전 page로 요청하는 경로가 있어 첫 추가 로딩에 같은 페이지가 다시 붙을 수 있다. 느린 느낌을 애니메이션으로 가리기 전에 이 계약부터 고쳐야 한다.
2. **코드 확인 — 검색/필터의 오래된 응답이 최신 상태를 덮을 수 있다.** 디바운스는 있으나 취소·응답 세대 검증이 부족하다. query key와 request cancellation을 도입한다.
3. **코드 확인 — 공통 재시도가 POST도 다시 보낸다.** 서버가 저장한 뒤 응답만 유실되면 중복 저장 또는 toggle 역전 위험이 있다. 읽기 재시도와 쓰기 멱등성을 분리한다. 실제 중복 발생 건수는 미확인이다.
4. **빌드 확인 — 프로필 청크가 무겁다.** MyAniPass 청크는 minified 422.69 kB, gzip 120.42 kB이고 통계 컴포넌트를 정적 import한다. 피드/서재 진입 시 필요 없는 차트는 탭 단위로 분리한다. 실제 체감 개선량은 아직 모른다.
5. **코드 확인 — 이미지·폰트 요청 정책을 단순화할 여지가 있다.** 작은 썸네일에도 covers_large 선택, 복수 폰트 CSS, 오래 스크롤한 항목을 해제하지 않는 지연 마운트가 있다. 실제 waterfall/DOM 측정 후 우선순위를 확정한다.
6. **코드 확인 — 백엔드 집계·이미지 경로가 확장에 취약하다.** 전체 engagement 집계 후 LIMIT, 댓글별 답글 조회, async route의 동기 외부 요청이 있다. API 실행계획과 event-loop 지연을 측정한 뒤 page-first 집계·batch 조회·I/O 분리를 한다.

### D. 디자인 작업보다 먼저 확인할 안전 문제

- **P0 / 코드 확인:** 인증 dependency 없는 관리 API가 사용자 인증 상태 변경과 이메일 포함 조회를 제공하며 앱에 등록되어 있다. 실제 운영 gateway 차단 여부는 미확인이다. 이 경로들을 공개 앱에서 제거하거나 중앙 관리자 권한을 강제해야 한다. 운영 데이터로 악용 여부를 시험하지 않는다.
- **P1 / 코드 확인:** 평점 수정이 기존 activity 삭제와 재생성 경로를 거친다. 좋아요·댓글·북마크의 activity_id 참조를 유지하지 못할 위험이 있다. ID를 보존하는 UPSERT와 요청 단위 transaction이 필요하다.
- **P1 / 코드 확인:** 평점 trigger의 user_stats JOIN이 오른쪽 테이블 키를 연결하지 않는다. 통계 오염과 불필요한 쓰기 위험을 격리 fixture에서 재현해야 한다.
- **P1 / 코드 확인:** 서버 startup에 중복 삭제·스키마/trigger 변경·일괄 인증이 섞이고 실패 후에도 health는 성공을 반환한다. versioned migration과 readiness를 분리해야 한다.
- 기본 비밀키 허용, OAuth 계정 연결/비밀번호 처리, 캐릭터 별점 상태 전이, 구·신 댓글 원천 혼재는 backend-audit.md에 별도 정리했다. 설정 위험과 실제 침해를 혼동하지 않는다.

## 2. 제품 방향: 기능 나열에서 취향 기록 여정으로

### 주 사용자와 핵심 행동

- 신규 사용자: 관심 작품을 찾고 내용/평점을 확인한다. 가입 전에도 서비스 가치를 이해해야 한다.
- 기록형 사용자: 본 작품을 빠르게 평가하고 보고 싶은 작품을 관리한다. 기록이 사라지거나 저장 여부가 모호하면 안 된다.
- 팬 커뮤니티 사용자: 캐릭터와 리뷰를 통해 취향이 맞는 사람을 찾는다. 스포일러·과도한 평가 활동 노출을 제어해야 한다.

핵심 반복 흐름: 발견 → 내 평가/저장 → 내 서재 → 다음 작품 발견. 피드·레벨·리더보드는 이를 보조한다. 새 추천 AI나 신규 소셜 기능 확대는 이번 1차 범위에서 제외한다.

### 추천 내비게이션

모바일 하단: 발견 / 평가 / 피드 / 내 서재.
데스크톱 상단: AniBite / 검색 / 발견 / 평가 / 피드 / 내 서재, 우측 알림·계정.

- ‘평가’ 내부에 작품 / 캐릭터 탭을 둔다. 기존 빠른 평가 흐름은 유지한다.
- ‘리뷰 작성’은 작품·캐릭터 상세와 평가 완료 상태의 후속 행동으로 둔다. 기존 작성 페이지는 바로가기/호환 경로로 유지할 수 있다.
- 리더보드는 피드 또는 프로필의 보조 메뉴로 내린다. 기능 삭제가 아니라 전역 메뉴 우선순위 조정이다.
- 기존 URL은 redirect/alias로 보존한다. 새 사용자와 기존 사용자의 행동 데이터로 기본 탭을 검증한다.

## 3. 화면별 개편안

### 3.1 발견·검색

첫 화면 순서: 검색 → 이어서 볼 내 목록(로그인 시) → 인기/현재 분기 → 장르·연도 등 필터 → 작품 목록.
- 추천 근거가 없으면 ‘맞춤 추천’ 대신 ‘인기 작품’처럼 사실대로 표시한다.
- 입력, 정렬, 장르/연도 필터는 URL에 보존한다. 상세에서 뒤로 가면 결과와 스크롤 위치를 복원한다.
- 검색 결과는 작품 / 캐릭터를 탭으로 구분하고 결과 수·더 보기 상태를 분명히 한다.
- 모바일은 카드/컴팩트 목록, 데스크톱은 카드 기본 + 목록 보기 옵션. 모바일에 다열 표를 그대로 축소하지 않는다.
- 검색 중 기존 결과를 유지하되 ‘검색 중’ 표시, 실패 시 입력·기존 결과를 보존하고 재시도. 빈 결과에는 필터 초기화/다른 검색어 제안.
- 검색 요청의 취소와 마지막 응답 우선 규칙을 UI 구현보다 먼저 보장한다.

### 3.2 작품 상세

모바일:
  뒤로 / 제목
  포스터 + 제목·연도·형식
  평균 평점·참여 수 / 내 평점 (명확히 분리)
  평가하기 / 보고 싶어요
  소개(접기) / 리뷰 / 캐릭터·시리즈
  화면 하단 평가 바로가기 — 키보드·하단 내비와 겹치지 않게 배치

데스크톱:
  좌측 포스터·내 평가 패널 | 우측 작품 정보·소개·리뷰
  시리즈·캐릭터·유사 작품은 본문 후순위

- 내 평가와 평균 평점을 색뿐 아니라 문구로 구분한다. 외부 평점이 있다면 출처·척도를 표시한다.
- 평균 평점은 참여 수와 함께 표시하고 무평가를 0점처럼 보이게 하지 않는다.
- 스포일러 리뷰는 기본 가림. ‘스포일러 보기’ 전까지 본문을 노출하지 않는다.
- 공개 상세에 타인의 비공개 서재/개인화 데이터가 섞이지 않도록 API 응답을 분리한다.

### 3.3 빠른 평가

- 포스터 + 읽을 수 있는 두 줄 제목 + 내 상태 + 명확한 평가 진입점을 기본 카드 계약으로 통일한다.
- 별점은 0.5 단위를 유지하되 모바일에는 숫자 피드백과 ±0.5 조정 또는 접근 가능한 slider/radio를 제공한다. 작은 별의 왼쪽 절반을 맞히는 방식만 강요하지 않는다.
- 같은 별을 눌러 삭제하는 숨은 동작 대신 ‘평가 지우기’를 명시한다. 실행 취소 제공.
- ‘평가하지 않음’, ‘보고 싶어요’, ‘관심 없음’을 별점 0과 구분한다.
- 상태 선택 즉시 시각 피드백을 주고 저장중/저장됨/실패를 구분한다. 실패 시 롤백하며 재시도할 값은 남긴다.
- 연속 평가 도중 카드를 즉시 없애서 목록이 튀지 않게 한다. 다음 카드 진행과 취소를 제어한다.
- 리뷰는 별점 후 선택 행동. 첫 평가를 위해 장문 입력을 요구하지 않는다.

### 3.4 피드·리뷰

- 피드/상세/프로필에 동일한 ActivityCard와 댓글 컴포넌트를 사용한다. 데이터 adapter는 있어도 표시 규칙은 같게 한다.
- 팔로잉 / 전체를 주요 필터로, 알림·저장은 각각 전용 진입점으로 정리한다.
- 같은 사용자의 짧은 연속 평가를 묶어 피드 독점을 줄이는 기능은 2차 실험으로 둔다. 원본 기록은 삭제하지 않는다.
- 좋아요·댓글·스포일러·작성 시각·수정됨 표시를 통일한다.
- 리뷰 작성 draft 보존, 이탈 경고, 글자 수, 오류 위치, 저장 후 결과 read-back을 명세한다. 비공개 초안을 분석 이벤트에 보내지 않는다.

### 3.5 내 서재·프로필

- ‘내 작품’ / ‘내 캐릭터’ / ‘기록’ / ‘취향 통계’를 분리한다. 첫 화면은 실용적인 기록/컬렉션을 우선한다.
- 원하는 상태로 필터·정렬하고 평가를 바로 수정한다. 탭·필터·스크롤 복원을 유지한다.
- 레벨은 보조 동기부여로 유지하되 화면의 주 정보를 차지하지 않게 한다.
- 차트는 통계 탭 진입 시 로딩한다. 평가가 적을 때 빈 차트 대신 통계에 필요한 조건을 설명한다.
- 사용자 프로필과 내 서재는 공통 표현을 쓰되 편집 권한을 명확히 나눈다.

### 3.6 로그인·온보딩·회복

- 언어 통일, label 연결, autocomplete=username/current-password, 오류 aria-live, 비밀번호 표시 토글과 적절한 계정 회복 경로.
- 제공자 로그인이 차단되면 반복 시도 대신 일반 지원 브라우저 안내. 이메일 비밀번호 방식은 해당 계정에서 실제로 지원할 때만 안내한다.
- 공유 상세 → 로그인 → 원래 상세로 복귀. 돌아갈 URL은 내부 경로인지 검증한다.
- 가입 직후 관심 작품 평가를 제안하되 건너뛰기 가능. 데이터가 없다고 기능을 막지 않는다.
- 401/403/404/오프라인/서버 오류/빈 목록을 서로 다른 상태로 표현한다.

## 4. 디자인 시스템 방향

목표: 포스터 중심의 차분한 다크 테마. 네온 효과나 장식 애니메이션보다 읽기·평가·상태 구분 우선.

- 팔레트: 현재 배경 #0A0E17, 표면 #141A26, 강조 #47B5FF, 평점 #F5C842를 출발점으로 삼는다. 최종 색상 조합은 실제 computed contrast 검사 후 확정한다.
- 강조색은 주요 행동과 선택 상태에 사용한다. 같은 화면의 모든 카드·버튼에 glow를 주지 않는다. 별점 금색을 성공/경고 색과 혼용하지 않는다.
- 본문 16px, 보조 정보 14px를 기본 설계안으로 하고 아주 작은 텍스트는 제한한다. 작품 제목은 두 줄 허용, 원제/번역 제목 우선순위를 언어별로 정의한다.
- 본문 폰트는 한글·라틴 공용 한 계열을 우선 검토하고 일본어 fallback/subset을 따로 정한다. 로고 글꼴을 본문에 확장하지 않는다.
- 여백은 4/8/12/16/24/32px 계열로 정리하고 인라인 숫자와 토큰의 중복을 줄인다.
- 콘텐츠 최대폭은 약 1200px 설계안. 피드·리뷰 읽기 영역은 640~720px 설계안으로 제한한다. 숫자는 현재 측정값이 아니라 시안 기준이다.
- 카드 포스터 비율, 제목 줄수, 상태 위치, skeleton 크기를 공통화한다. 360px 모바일에서 2열이 실제 입력영역과 양립하는지 검증하고, 어렵다면 평가 화면은 1열로 바꾼다.
- 모바일 주요 조작 목표 44×44 CSS px, 아이콘 이름, focus-visible, 200% 확대, prefers-reduced-motion 지원. 전역 모든 링크에 min-width를 강제하는 대신 조작부별로 설계한다.
- 공통 컴포넌트: AppShell, Button, FormField, SearchField, SegmentedTabs, AnimeCard, CharacterCard, RatingInput, ActivityCard, Dialog/Sheet, Toast, EmptyState, ErrorState, Skeleton.
- 각 컴포넌트는 default/hover/focus/pressed/disabled/loading/error 상태를 갖는다. 전역 속성 부분일치 selector로 색을 덮는 방식은 제거한다.

구현 전에 모바일 발견·작품 상세·빠른 평가 3개 핵심 시안을 같은 디자인 토큰으로 비교하고 사용자 검토를 받는다. 이번 문서는 시안 구현 완료물이 아니다.

## 5. 반응속도 목표와 측정 계획

### 현재 확보한 실제 수치

- `npm run build`: 성공. 엔트리 JS gzip 98.41 kB, MyAniPass gzip 120.42 kB. 이것은 빌드 산출물 크기이지 실제 총 전송량이 아니다.
- `npm run lint`: 실패, 169건(오류 151 / 경고 18). 이 숫자를 사용자 장애 수로 해석하지 않는다.
- `npm audit`: 20건(low 2 / moderate 6 / high 12 / critical 0). 런타임/개발 의존과 advisory 적용 조건을 분류해야 한다. 12건의 실제 공격 가능성이 입증됐다는 뜻이 아니다.
- 공개 로그인의 단일 비제한 측정은 별도 login-desktop-evidence.json에 저장했다. 캐시 상태가 통제되지 않았고 인증 후 페이지 성능을 대표하지 않아 전체 서비스 속도 판단에 사용하지 않는다.

### 개선 후 수용 목표 — 현재 달성치 아님

- 실제 사용자 모바일 p75: LCP ≤2.5초, INP ≤200ms, CLS ≤0.1.
- 평가/저장 클릭의 로컬 피드백 100ms 이내를 목표로 한다. 서버 확정 전에는 ‘저장됨’이라고 표시하지 않는다.
- 대표 staging 데이터와 고정 부하에서 주요 목록·저장 API p95 ≤500ms를 초기 성능 예산으로 제안한다. 외부 제공자 요청은 별도 예산으로 분리하고 기준선 측정 후 현실화한다.
- 정상 경로에 의도하지 않은 중복 요청 없음, mutation 중복 없음, 응답 역전에도 최신 필터 보존.
- 프로필 기본 탭의 네트워크 요청에서 통계 전용 차트 청크 제외. 명목상 번들 크기 감소율 대신 해당 요청이 실제 제거되는지 확인한다.

### 측정 절차

1. 같은 빌드·fixture·브라우저로 발견/상세/평가/피드/서재를 고정 시나리오화한다.
2. cold/warm cache를 나누고 390px 모바일 네트워크/CPU 제한 조건을 기록해 여러 번 측정한다. 실제 기기 검증을 별도로 한다.
3. LCP 요소, waterfall, API timings, long task, React commit, 스크롤 전후 DOM 수를 기록한다. 로컬 한 번 측정을 p75 필드 지표로 부르지 않는다.
4. 이미지 크기/캐시, 폰트, 차트 분할, API 집계를 각각 따로 바꾸어 전후 비교한다.
5. 배포 후 개인정보를 제외한 Web Vitals와 오류율을 수집한다. 검색어·리뷰 본문·비공개 취향 기록은 원문 분석 이벤트에서 제외한다.

## 6. 기술 리팩토링 설계

기본 유지: React + Vite + FastAPI. 실제 package.json은 React 19이며 README의 React 18 설명은 오래됐다. SQLite를 즉시 다른 DB로 옮길 근거는 아직 없다.

프런트엔드:
- features/catalog, ratings, activity, profile + shared/api, ui, i18n 경계.
- 먼저 현재 API 계약 adapter와 회귀 테스트를 만든 후 UI를 옮긴다. 폴더 이동만으로 개선됐다고 하지 않는다.
- 서버 상태는 query key/취소/캐시/무효화가 일관된 계층으로 통합한다. TanStack Query 같은 라이브러리 도입 여부는 작은 탐색 화면 실험으로 결정한다.
- 화면 로컬 상태는 모달·선택·초안 등에 한정한다. 평점 변경 시 상세/서재/피드/통계의 갱신 범위를 한 곳에서 정의한다.
- 현재 lazy route, URL 탭 복원, 이미지 fallback, 좋아요 낙관적 갱신/롤백은 보존한다.
- 거대한 프로필/상세 페이지를 도메인 단위로 분할하고 구 handler와 실제 사용 경로를 구별한다.

백엔드·데이터:
- 평점/리뷰 원본과 활동 표시 데이터의 책임을 명시하고 쓰기 경로를 단일 command 서비스로 모은다.
- 기존 통합 activities API는 이미 있다. 오래된 REFACTORING_PLAN.md의 미완료 체크박스만 보고 또 만들지 않는다.
- activity ID 보존, rating/status 제약, 댓글 parent 소속/깊이 검증, 멱등 like/unlike, transaction을 우선한다.
- 구 API는 새 canonical 서비스 adapter로 바꾸고 소비자가 없어졌을 때 제거한다.
- ID를 이관할 때 `(legacy_table, legacy_id) → canonical_id` 매핑을 남기고 댓글 부모·좋아요·북마크·알림을 함께 검증한다.
- migration은 startup 밖의 versioned release job으로 이동한다. liveness와 DB/schema readiness를 분리한다.
- DB 교체, SSR 전면 이식, 새로운 추천 엔진, 앱 개발은 1차 범위에서 제외한다. 공개 상세의 검색/공유 수요가 검증되면 그 경로만 SSR/prerender를 검토한다.

## 7. 실행 순서와 완료 기준

기간은 팀 규모·로그인 후 검수·운영 데이터 상태가 미확정이므로 약속하지 않는다. 아래는 순서와 출시 gate다.

| 단계 | 우선순위 | 산출물 | 완료 기준 |
|---|---|---|---|
| 0 안전 확인 | P0 | 관리 권한/환경 설정 목록, 격리 테스트 DB, 백업·복원 절차 | 비인가 관리 요청 401/403 또는 경로 제거; DB 무변경; 비밀키 기본값 배포 거부; 복원 연습 |
| 1 정확성 복구 | P1 | Browse 계약, 최신 응답 우선, mutation 정책, ID 보존 | 첫 추가 페이지 중복 없음; 정렬 실제 반영; 응답 유실 뒤 중복 저장 없음; 별점 변경 후 댓글/좋아요/북마크 유지 |
| 2 핵심 UX·디자인 | P1 | 모바일 발견/상세/평가 시안, 공통 토큰·RatingInput·Dialog | 터치/키보드 반점 평가; 초안/필터/복귀 유지; 모달 focus; 사용자 시안 승인 |
| 3 점진적 적용 | P2 | 서재/피드/캐릭터까지 공통 컴포넌트 적용 | 구 URL 유지; 스포일러 정책; 화면별 상태 일관성; 360/390/768/1280/1440 반응형 검수 |
| 4 성능·출시 | P2 | 이미지/폰트/차트/API 전후 측정, staging 회귀 결과 | 합의한 성능 예산, lint/build/test gate, 오류율·데이터 정합성 관찰 및 rollback 연습 |

가장 먼저 구현할 세 작업은 ‘관리 API 차단/권한 테스트’, ‘Browse 요청 계약과 페이지 중복’, ‘평점 수정의 activity ID 보존’이다. 디자인 탐색은 병행할 수 있지만 새로운 UI의 운영 배포는 이 정확성 gate 뒤에 둔다.

## 8. 검수·배포 체크리스트

핵심 시나리오:
- 비로그인 발견/공유 상세 → 평가 시 로그인 → 원래 위치 복귀.
- 한글·영문·일본어 작품/캐릭터 검색, 검색 삭제, 빠른 필터 전환, 뒤로 가기, 첫/끝 페이지.
- 평가 생성/수정/삭제/상태 변경, 반점, 빠른 연속 클릭, 저장 중 연결 끊김, 응답 유실.
- 별점만 바뀌어도 같은 리뷰·댓글·좋아요·북마크·알림 연결 유지.
- 스포일러, 빈/긴 리뷰, 초안 보존, 다른 활동 댓글에 잘못된 parent 입력 거부.
- 내 서재와 타인 프로필의 권한, 일반 사용자 관리자 경로 거부.
- empty/error/offline/401/403/404 구분, retry, 세션 만료.
- 모바일 하단 내비·안전영역·가상 키보드·배너 겹침, 200% 확대, reduced-motion.

배포:
- 운영 DB는 일관된 snapshot으로 백업하고 별도 환경에서 복원을 확인한다. WAL 사용 중 DB 파일 하나만 복사하지 않는다.
- 먼저 확장형 schema와 호환 adapter 적용 → staging 비교 → 일부 읽기 경로 전환 → 관찰 → 구 경로 제거.
- 단순 행 총계뿐 아니라 사용자/작품별 상태·리뷰 내용·댓글 계층·소셜 참조를 비교한다.
- 읽기 feature flag를 rollback 수단으로 준비한다. 새 쓰기가 들어간 뒤 오래된 DB 백업을 무작정 복원하지 않는다.
- 운영 변경·마이그레이션·배포는 별도 승인 후 실행한다. 이번에는 실행하지 않았다.

제품 검증 지표:
- 방문→첫 작품 상세→첫 평가 완료 퍼널, 평가 저장 성공률, 평가당 소요 시간, 검색→상세 진입, 서재 재방문, 리뷰 초안 손실/실패율.
- 현재 기준선은 없다. 신규/기존 사용자를 나누어 관찰하고 기존 빠른 평가 사용자 작업량이 악화되면 설계를 되돌린다.
